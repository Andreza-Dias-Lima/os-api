API Ordem de Serviço

Arquitetura resiliente com FastAPI, PostgreSQL, Idempotência e Outbox Pattern

Problema e Objetivos

  • Evitar duplicidade
  • Garantir consistência
  • Processar eventos de forma confiável
  • Fornecer rastreabilidade ponta a ponta

Arquitetura

Cliente → API → Service → Repository → PostgreSQL → Outbox → Worker

Banco de Dados

PostgreSQL escolhido por ACID, transações e confiabilidade.

  • ordens_servico
  • idempotency_keys
  • outbox_events

CAP Theorem

Estratégia CP: Consistency + Partition Tolerance.

Melhor falhar temporariamente do que persistir dados inconsistentes.

Idempotência

Mesma chave → mesma resposta → nenhuma duplicidade.

Outbox Pattern

Ordem e Evento persistidos na mesma transação.

Observabilidade

Correlation ID propagado por todo o fluxo.

SLA e SLO

SLA 99.5%
P95 < 300ms
99% eventos < 1 min

Monitoramento

  • Prometheus
  • Grafana
  • OpenTelemetry
  • Loki
  • Tempo

Trade-offs e Limitações

  • Fake Requester Client
  • Worker local
  • Sem DLQ
  • PostgreSQL único
  • Escolha por consistência em vez de disponibilidade

Roadmap

  • JWT + RBAC
  • Retry e DLQ
  • Redis
  • Kafka
  • CQRS e Sagas

A solução prioriza consistência, confiabilidade e observabilidade.
